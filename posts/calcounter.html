CALCOUNTER / ELECTRON / PROJECT STORY

A nutrition tracker designed to stay out of the way

CalCounter turns USDA nutrition data into a focused desktop workflow for logging food, tracking daily goals, and keeping history locally.

6 MIN READELECTRON / JAVASCRIPT / USDA APIWINDOWS + MACOS BUILDS

CalCounter began as a straightforward web interface and grew into a packaged desktop application. The core idea stayed simple: make daily calorie tracking quick, keep the user’s history on their own computer, and use an authoritative public data source when nutrition values are needed.

What it does: searches USDA FoodData Central, converts serving quantities, logs calories and macronutrients, supports manual food entries, tracks multiple days, and shows progress against a configurable daily goal.

The user workflow

  1. Create or select a day.
  2. Describe a food, amount, and unit or enter known calories manually.
  3. Choose the closest USDA match from a ranked result list.
  4. Review consumed, goal, and remaining calories in the daily log.
  5. Switch between days to see a locally stored history.

Making USDA data useful

The application sends food searches to the USDA FoodData Central API and normalizes the results into calories, protein, fat, and carbohydrates for the requested serving. It supports grams, ounces, cups, tablespoons, slices, and pieces.

The result ranking is more than a basic API pass-through. CalCounter scores descriptions by query-token matches, data-source priority, exact matches, contradictory ingredients, and prepared-food terms. That helps a search for a simple ingredient avoid returning an unrelated branded meal at the top of the list.

A safer Electron boundary

The browser-facing UI does not receive Node.js access. The Electron window runs with context isolation enabled and node integration disabled. A small preload bridge exposes only the operations the interface needs: nutrition search and API-key status, save, and clear actions.

The USDA key is read and written by the Electron main process. Local token and configuration files are excluded from packaged builds and ignored by Git, keeping real credentials out of the repository.

Local-first by default

Daily logs and calorie goals use local storage. There is no account requirement and no hosted database collecting food history. That keeps setup light and makes the privacy model easy to understand: the log stays on the computer running CalCounter.

From webpage to installable app

Electron Builder packages CalCounter as a Windows NSIS installer and a macOS DMG. A GitHub Actions workflow runs the Windows and macOS builds on their respective hosted environments and uploads the distributable artifacts. The app can therefore keep a web-technology interface while behaving like a focused desktop tool.

What I would build next

  • Add automated tests around serving conversion and USDA-result ranking.
  • Support data export and import without adding a required cloud account.
  • Add signed release automation for smoother Windows and macOS distribution.
  • Expand goal tracking beyond calories while keeping the interface intentionally small.

CalCounter is public on GitHub, including the Electron application, packaging configuration, and cross-platform build workflow.
